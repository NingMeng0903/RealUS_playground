## S 卡住的已知边界

- S/001 只有 prepare_begin，未出现 standoff_ready，没有 recorder/QP 数据，尚未进入 S 扫描。
- controller 末尾为 `[MODE] TRACK_CARTESIAN`、`[STOP] external stop`，之后未出现新的 `[MODE] MOVEJ`。
- 这个 external stop 在 daemon 中用于模式切换时结束原 runner，随后调用 `_coordinated_brake()`；仅凭文字不能当作操作者按了急停。
- `Command rejected: 1` 是通用 ERR_CONTROLLER；安装等待期间心跳过期也会返回 1，不能据此解释成机械臂或 S 求解器返回的错误码。
- 后续心跳年龄从 4.816 s 增长到 18.939 s，说明期间控制器状态未更新；这些 retry 在 capability preflight 就退出，没有发送新的请求。
- controller 输出出现过 FA24/encoder HOLD 和 `modbus error (3x): not connected`，停止链的地轨 I/O 是重要排查对象，但没有带时间的堆栈证实它就是最后阻塞函数。
- 用 C 结束时的实际关节姿态、匹配的 TCP 缓存及配置中的姿态吸引点离线计算 S standoff IK，0.10945 s 找到满足目标的解；FK 与记录中的 C 末端 pose 一致。见 `offline_standoff_ik.json`。此检查没有重建现场实时姿态吸引点、设备 I/O 或停机线程，不能证明现场没有其他规划/切换问题。

目前可定位为旧任务结束到新 MOVEJ 安装之间的停止/清理/编译链路失去响应。仍需卡住当时的线程调用栈，才能确定具体阻塞点并修复；现有证据不支持把 S 失败归因于 S 形状、confidence 计算或新扫描的能量耗尽。
