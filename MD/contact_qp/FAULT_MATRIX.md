## 每次注入必须保存的事实

对每个 candidate 保存 `candidate_id/native_request_seq/stop_epoch/expiry/H`、nominal/qp/sent/predicted/measured 五种速度、最终 arm/rail payload 和时间。设备发布状态分别记为 `NONE`（能证明未进入发送）、`ACCEPTED`（相应软件/传输接口接收）、`UNKNOWN`（可能进入发送但结果不明）；机械臂调用返回 0 不代表已经测得运动，rail `commit_reservation=True` 仅代表目标已对 worker 可见。

rail 还必须保留 `command_rx_seq/command_processed_seq/command_written_seq/drive_write_seq/command_write_mono_s`。这些在 `RailServoSample`/execution feedback 已有，接收、处理、设备写入不能合并成一次 ACK。native 的 `cmd_ack/out.seq` 是求解/控制命令协议响应，也不是 arm/rail 设备执行 ACK；`NativeWbcClient._published_q_cmd` 当前在解析候选时即赋值，名称本身不能证明已发送。

每个物理能量区间有独立 interval identity、测量来源/有效性和预留归属。日志分别保存 settled balance、outstanding reservations、stopping reserve 和 free balance，不把释放预留记成充能。令 C_i 是按冻结物理符号计算的保守净消耗，结算只做一次 `E_next=E−C_i`，并在同一个账本操作中释放该区间对应预留；负 C_i 的回流也只能在保守结算后变成可用余额。

## 当前缺口与验收边界

1. **停止代次还未贯穿发送链。** runner 的 `fault_epoch=[0]` 仅由 `_watchdog_trip()` 增加；局部 `_fault_stop()` 本身没有加代次。peirastic daemon 的 `_fault_epoch` 是另一个对象，不能当作已共享的 fence。当前 runner 的一次 pre-send 检查在 rail target 修改、reserve、arm send、rail commit 之前，不等价于每个设备操作前重检。
2. **rail 预留是软件所有权，不是执行原子性。** 真桥会在 commit 重检 armed/calibrated/panic/stop/abort，并在 hold、立即命令和新 tracking session 清除 `_reserved`。但 reservation 没有 candidate sequence/epoch/expiry；worker 约 2666 拍下 follow/command_seq，约 3301 写 RPM 前没有再比较这些值。已有 reservation 单元测试不能证明 stop 与 worker I/O 的竞争安全。
3. **native 的 pending commit 没有请求身份匹配。** Python 把 commit seq 写进 `cmd_u[0]`，但 [inner.cpp](../../rm75_control/native/wbc_rt/src/inner.cpp) `InnerLoop::handle_pending_flags(uint32_t flags)` 仅在 `pending_valid_` 时按 flag 恢复当前 pending。C++ STEP 路径未把该 commit id 传给 pending handler。`test_native_pending_commit_is_wired` 目前是源码字符串存在性检查，不是重复/错序 ACK 的行为测试。
4. **迟到 native 回复可能配上新调用参数。** `_update_locked` 的 inflight 分支以旧 seq 读取回复，却把当前 `twist/q_meas/qdot_ff/kwargs` 传入 `_accept_ok_step`。新证书/H/预算必须绑定原候选；现有 soft-miss 恢复测试只检查恢复状态，不检查这项绑定。
5. **没有最终通用 Cartesian 行的端到端验收。** 当前 native protocol v8 仍是 616/1472 字节，core `TwistConstraints` 虽有 frame/sequence/stop_epoch，但 native 还未接收这些泛型约束。新测试必须覆盖 native 所有后处理后及 Python 最终 target/coast/snap 后的两种映射。
6. **无现成完整发布协调 fixture / 能量账本 fixture。** 对 guard 调用顺序的 `inspect.getsource` 测试只能保护源码顺序，不能覆盖 arm 已执行后 rail 失败、未知发送结果或旧 I/O 越过 stop。Stage 3 应以这里真实的 helper/bridge/native peer/测量对象拼装执行级注入；不得用返回布尔值的纯假 coordinator 宣称生产链通过。
7. **参考时钟还属于旧 runner governor。** 当前约 7219 使用 `t_ref += reference_time_step(dt_wall_actual,scale)`，native timeout coast 通过 `path_reference_should_freeze` 置 scale=0；这还不是合同的 owned accepted-alpha clock。Stage 3 必須同时断言原 nominal 状态与新参考时钟，不能只看 inner `q_cmd` 没变。

验收日志必须能重建 `candidate → device facts → measured/exposure interval → one settlement`。对 partial/unknown，允许记“目前不能认证”，不允许把两个独立设备变成假原子事务。使用 fake drive、隔离 SHM peer 或数学执行模型能验证软件和指定合成界下的语义；没有真实测得的有限发送/停止/误差上界时，硬件仍是 MONITOR/UNVERIFIED。
