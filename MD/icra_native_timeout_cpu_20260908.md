# native_timeout：CPU 调度检查与启动修正

## 故障证据

用户提供的 `qpik_fault_1788877223308047123_677157.json` 对应北京时间
2026-09-08 22:20:23，阶段是 `payload_id_dt_x`，即载荷辨识运动。
它说明问题也发生在辨识期间，不能仅凭这个快照归因于 HDF5 录制。

| 记录 | 数值 | 解释 |
|---|---:|---|
| native 请求往返 | 51.898 ms | 已超过现有约 50 ms 请求年龄上限 |
| native_cpu_ms | 3.24 ms | 诊断区间内 native 实际获得 CPU 的累计时间 |
| native_runqueue_ms | 48.35 ms | native 已可运行，但仍等待 CPU 的累计时间 |
| last_completed_solve_ms | 3.30 ms | 上一个已接受请求的求解时间 |
| 反馈年龄 | TCP 5.0 ms / 滑轨 9.9 ms | 该快照中的反馈年龄 |

这强烈支持调度等待，而非本次 QP 计算用了约 52 ms。计数从请求提交前
累计到超时诊断采样，可能包含停止/快照期间的少量时间，不是与回复原子同步的
求解计时。当前失败结果的 `qp1/qp2=not_run` 是超时状态，不表示实际求解耗时为零。
`observed_reply_seq` 后来追上请求序号，也不证明结果在过期前可用。

瞬间的可运行任务竞争会产生偶发长尾，整机平均 CPU 利用率低也不能排除。
native 当前是单线程；多给几个允许 CPU 并不会直接把一次 QP 并行加速。
CPU 绑定限制该线程在哪里运行，并不禁止其他应用使用同一 CPU。

## 只读现场检查

本机有 32 个逻辑 CPU。控制线程使用 CPU 2，native 使用 CPU 4，分别属于不同
物理核心；其 SMT 同胞为 3 和 5，后台程序应避开整个 2/3/4/5 集合。

此次修改前的宿主机 `/proc` 检查发现：

- 控制器 PID 832148 主线程确实绑定 CPU 2，但六个辅助线程仍允许使用全部 CPU。
- native PID 833065 确实绑定 CPU 4，nice=0，单线程。
- 辨识 PID 833797 共 65 个线程，均允许使用全部 CPU，nice=0。三秒采样时多数
  数值线程并未运行；65 个线程不是 65 个忙碌核心，也不能据此认定它是历史故障的唯一来源。
- 超声 PID 717724 已使用后台 CPU 0/1/6–31、nice=10，前一次超声入口修正已生效。
- native 三秒采样的 CPU 时间累计约 1001 ms，等待 CPU 累计约 105 ms；
  **105 ms 是整个采样区间的累计值，不能解释为单次卡顿 105 ms**。

未对正在运行的进程执行改优先级、迁移、终止或重启；没有发送机器人命令。
现场样本能确认资源配置缺口，不能重建过去那 48 ms 内具体是谁占用了 CPU。

## 已修改的启动入口

- `peirastic.apps.run_controller` 先解析实际 `--config`，在导入数值库、SDK 和
  daemon 前将初始化线程移到后台 CPU，使此时创建的辅助线程继承后台掩码。
  控制循环和 native 随后仍使用原有 CPU 绑定，控制器 nice 不变。
- `peirastic.apps.identify_payload` 在导入 NumPy/SciPy 前应用后台 CPU、nice=10
  和单线程数值池设置。原辨识命令保持不变。
- `peirastic.apps.gamepad` 提前限制数值线程并避开控制核，保留手柄原 nice。
- 已有录制、预览、超声入口继续使用后台设置。

这些都是下次启动生效的设置，不能修改已有线程，也不是系统级 CPU 独占。
控制线程绑定之后新建的某些实时辅助线程仍可能跟随该绑定。
未改变 20 ms 首次等待、约 50 ms 请求年龄保护、力控参数或急停恢复逻辑。

## 检查与离线任务入口

```bash
cd /media/camp/EXT_DRIVE/ICRA_YM/script
bash run.sh cpu-check --seconds 3
bash run.sh cpu-check --seconds 3 --json > /tmp/icra-cpu-check.json
```

该命令只读 `/proc`，输出实际线程 CPU 掩码、优先级和采样期间的调度累计值，
不连接机器人 IPC。后台候选列表表示允许使用保留 CPU 的程序；它不是历史肇因清单。
短时未见排队也不是最坏延迟合格证明。

离线重建、图像分析等任务可用 `bash run.sh background` 后接原命令启动。
例如 `bash run.sh background python offline_job.py`，其中 `offline_job.py` 替换为
实际任务。这个入口只限制新启动的任务及其继承线程/子进程，不用于控制器/native。
采集时避免同时启动未约束的训练、渲染、批量图像处理及辨识任务。

更新后的控制器、手柄及辨识入口需要在下一次使用时重新启动才生效。
之后应在无人接触、空间已确认的条件下对照控制周期、native 等待和反馈丢样，
复现原负载检查长尾。如仍出现明显调度等待，再依据调度跟踪评估系统级 CPU 隔离；
不能单靠增大超时或任意设置实时优先级来掩盖。

两次 Ctrl-C 后的 `weakref`/Torch `atexit` 堆栈发生在进程清理阶段；这段截断堆栈
没有证明它导致了先前的 native 超时。

本次 CPU 修改不解除[此前异常下压事故](icra_scan_incident_20260908.md)的实机验证要求，
仍不能据此恢复人体批量自动采集。
